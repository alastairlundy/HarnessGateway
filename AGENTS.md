# AGENTS.md — HarnessGateway

CLI (`harnessgateway`) that launches agent harnesses (OpenCode, Kilo, Copilot CLI, Pi) pointed at a chosen provider (OpenAI/Anthropic-compatible endpoint). The launcher currently owns the whole codebase — don't invent a Proxy project yet.

## Build & test

- Solution is `src/HarnessGateway.slnx`, targeting **net10.0**. Use `--solution`, not a repo-root `.sln` or positional project path.
- Tests run on **native Microsoft Testing.Platform** (`global.json` pins `test.runner`), framework is **TUnit** (not xUnit/NUnit):

  ```bash
  dotnet test --solution src/HarnessGateway.slnx
  dotnet test --solution src/HarnessGateway.slnx --no-build --treenode-filter "/*/*/SkeletonTests/*"   # one class
  ```

  No `--` bridge separator (that's VSTest-mode syntax and fails here). TUnit class filtering is `--treenode-filter`; `--filter-class` fails with MTP exit code 5.
- Assertions are `await Assert.That(...)`. Known pre-existing warnings — don't add more of the same: `TUnitAssertions0005` (constant value in `Assert.That`, e.g. `LaunchExitCodeTests`), CS0618 for obsolete `HasCount()` (use `Count()`).
- Package versions come from CPM (`src/Directory.Packages.props`) — never add `Version=` on a `PackageReference`; add a `PackageVersion` there instead.

## Structure

- `HarnessGateway.Launcher` — `OutputType=Exe`. Entry: `Program.cs` + `Commands/` (System.CommandLine) + `Wizard/` (Spectre.Console).
- `HarnessGateway.Launcher.Core` — domain logic (Adapters, Providers, Settings, Launch, Execution, Configuration). Referenced by the exe; both are `InternalsVisibleTo` the tests.
- `HarnessGateway.Installer` — WiX project that builds the Windows MSIs (`harnessgateway-<rid>.msi` for win-x64/win-arm64; one solution build produces both via a second RID pass). It publishes the Launcher self-contained as its payload, so the MSI shape follows the Launcher, never restated. Windows-only: on other platforms it evaluates/restores but builds nothing, keeping the cross-platform CI matrix green. The MSIs are attached by `publish-release.yml` — `dotnet-releaser` produces only the archives and Linux packages, never installers.
- Per-harness behavior lives in `Core/Adapters/*Adapter.cs`, one class per harness: detection, config actions, launch plan. Adding a harness = new adapter class + add it to the `List<IHarnessAdapter>` in `Program.cs` + tests (`HarnessKind` already has `Cli` and `Gui`).
- `HarnessMetadata.Name` is a **display label** ("GitHub Copilot CLI") and is **not** user input. `CommandName` is the harness identifier (`copilot`); `Aliases` adds extra accepted spellings (`claude`, `github-copilot-cli`). Harness lookup goes through `HarnessLookup.Resolve`, which matches `CommandName` + `Aliases` case-insensitively and never `Name` — so `launch copilot` works and `launch "GitHub Copilot CLI"` exits 3 by design. `LaunchCommand`'s harness help text is **generated** from the registry (`BuildHarnessDescription`), never hand-written; `Shipped_adapters_resolve_their_own_command_names` gates that invariant. The wizard lists `Name` but returns `CommandName` in `WizardResult.AgentCommandName`, so the launch path only ever sees identifiers.
- "Did you mean" hints on both the agent and provider paths share `Core/Text/CloseMatch.cs` (prefix, then Levenshtein within 2). Non-contractual UX: tests must not pin hint text.

## CLI surface & gotchas

- `launch <harness> [--provider NAME] [--endpoint URL --protocol P --model M --persist config|model] [-p|--print [PROMPT]]`; `--endpoint` and `--protocol` are only valid together (the `--backend` spelling no longer parses). The `config` surface is `show`, typed-key `get`/`set` (closed key set: `defaultProvider`; read-only `schemaVersion`/`providers`; `providers.<name>.endpoint|.protocol|.defaultModel`; models are deliberately not scriptable), and the top-level `provider add|list|remove|set-key|clear-key` verbs plus `provider model add|remove|list <provider>` - user-facing docs live in the README's Configuration section; the command sources remain the normative reference. `config set defaultProvider` is the sole default-pointer write path; `provider remove` deletes the stored key (a key-deletion failure is reported, never blocking).
- **Two launch modes, decided by `LaunchFlow.ModeRefusal` before anything is planned.** Without `-p`/`--print` a Kind=Cli harness runs as an interactive session through `ILaunchRunner.RunInteractiveAsync` (console-shared handles, no timeout) — only while `ITerminalProbe` reports a real terminal on stdin and stdout, else the `TerminalRequired` refusal (exit 13, the one appended exit code). With `-p`/`--print` the launch runs buffered through `RunWithoutTimeoutAsync` (output echoed at exit, no terminal needed) and requires the `INonInteractiveLaunchAdapter` capability — implemented by claude-code, opencode, kilo, copilot, codex (`pi` and the GUI harness refuse, exit 2) — plus a prompt, from the flag's value or stdin when the value is omitted (`PrintPromptMissing`, exit 2; presence of the option, not its value, marks the launch — detected with `ParseResult.GetResult`). CliInvoke quirk proven empirically: a non-empty `ProcessConfiguration.ArgumentList` makes the library ignore the `Arguments` string, so print plans set only `ArgumentList` (entries stay one argv element whatever the prompt contains), and an interactive spawn must set `WindowCreation = true` — with the property default (`false`) CliInvoke gives the child console handles but **no console window** on Windows (`GetConsoleWindow()` = 0), so a TUI paints invisibly behind a bare caret (`LaunchRunner.InteractiveConfiguration`).
- **`launch <harness>` is wired through `LaunchCommand`'s own action, not the root's**: System.CommandLine runs the matched subcommand's action, and the root action can never read a child command's tokens — the root only handles the no-args wizard. `Program.cs` constructs the orchestrator and registers it on the subcommand; invoking `LaunchCommand` without that wiring is a loud failure, not a silent no-op. Orchestrator behavior itself is covered by `LaunchOrchestratorTests` (calls `RunAsync` directly); the parse-and-invoke wiring is covered by `LaunchCommandInvocationTests`.
- No-args invocation — and `launch` with no harness and no options — runs the interactive wizard (both entry points share `RunWizardAsync` in `Program.cs`; options without a harness still fail validation so the wizard fallback can't swallow a flag). The wizard is write-free: it returns a `WizardResult` and never saves settings. The wizard refuses unavailable harnesses at the harness step with the install hint and aborts (never re-prompts forever) when no available harness can be a valid pick. Wizard I/O goes through `IConsoleAbstraction`; tests enqueue scripted input via `TestConsole.EnqueueChoice/EnqueueText`. `ConsoleChoice.Annotation` is raw text — the presenter (`SpectreConsoleAbstraction`) owns the parenthesised rendering, so don't wrap it at the call site.
- Config-file writes must flow through the orchestrator + `BackupService`: backup before write, restore on exit unless `--persist config`; `SelfHealAsync` replays leftover backups at each launch (crash recovery). Harness env-var configuration rides on `LaunchPlan.Process.EnvironmentVariables` (child-process scope) — the launch path never mutates the launcher process env.
- Process launching uses **CliInvoke** (`ProcessConfiguration` + `CliRun.RunAsync`) — the repo migrated off `System.Diagnostics.Process`; keep it that way.

## Conventions & gotchas

- **Exit codes are a documented contract** (README table, enum in `src/HarnessGateway.Launcher/Models/LaunchExitCode.cs`: 0 and 2–13 — append-only). Don't renumber or add without updating README. Any unhandled exception *inside the orchestrator's launch flow* also returns 7 (ConfigRestoreFailure) — check stderr for `Launch failed:` before assuming a restore bug; user-rectifiable refusals (protocol mismatch or an unlisted model → exit 3, Codex provider-block collision → exit 10) are separate classes that don't use that prefix. LaunchCommand's missing-orchestrator guard is the deliberate exception: unreachable in production wiring, it throws `InvalidOperationException` with no catch, surfacing as a raw unhandled exception — a loud wiring bug, not a user-facing exit code.
- Settings file is `HarnessGateway-launcher.json` in the per-OS config dir (`%APPDATA%\HarnessGateway` / `~/Library/Application Support/HarnessGateway` / `~/.config/HarnessGateway`). API keys live in the platform credential store behind `ISecureKeyStore` (`Core/Settings/Security/`); the JSON holds only opaque references — never write secret material into settings.
- Standing "we deliberately don't do this" refusals are documented in `docs/agents/out-of-scope.md` — check it before proposing a new flag, verb, or behavior. Historical design decisions are in git history, not in the working tree.
- Style is mixed: Use explicit types in new code and code refactors. File-scoped namespaces everywhere.
- Legacy names linger from the LmProxy → HarnessGateway rename: old `LmProxy.AgentLauncher.*` names persist in bin/obj artifacts and test-report filenames. Don't resurrect them.
- CI is three workflows in `.github/workflows/`: `ci.yml` (push to main + every PR — restore, Release build, full TUnit suite, new-Meziantou-warnings gate with an inline baseline on Linux only; runs as a cross-platform matrix on ubuntu/windows/macos with `fail-fast: false`), `draft-release.yml` (push to main; **disabled and stale** — superseded by the per-OS AOT matrix in `publish-release.yml`, rework it against that pipeline before re-enabling), and `publish-release.yml` (`workflow_dispatch` only — asserts the tag matches the csproj `<Version>`, then builds every artifact from the tagged commit and attaches them to the hand-created draft before flipping it to published; the final `publish` job runs no builds). Release binaries are **Native AOT** (`PublishAot=true`, single ~10 MB exe; `IsAotCompatible` gates the trim/AOT analyzers on every build). AOT cannot cross-compile across OSes, so publish-release runs one job per OS: windows (win-x64 native + win-arm64 cross-arch → zips, plus the WiX MSIs whose payload publishes AOT via the wixproj), ubuntu (dotnet-releaser scoped to Linux in `dotnet-releaser.toml` → tar.gz + unsigned deb/rpm; linux-arm64 cross-compiles with the documented multiarch toolchain step; also runs the TUnit suite against the tagged commit), macos (osx-arm64 native + osx-x64 cross-arch via Xcode → tar.gz). Each build job smoke-runs the binary it can execute on its own runner (win-x64, linux-x64, osx-arm64); win-arm64/linux-arm64/osx-x64 ship without execution. Artifact-affecting values stay explicit: `dotnet-releaser.toml` owns the Linux shape, the workflow scripts own the win/osx archive naming (version-less `harnessgateway-<rid>.zip|.tar.gz`, files at the archive root); NuGet/brew/scoop/coverage/service disabled. Keep new commands lean — the plan is a unified CLI rename when proxy-server verbs arrive (see TODO.md).
